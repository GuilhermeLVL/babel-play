# Internacionalizar a interface

Estado em 2026-09-03. A interface nasceu inteira em português; este documento é o mapa do que já
funciona, do que falta e de por que o caminho é este.

## A decisão que torna o trabalho possível: a chave é o texto português

`t('Jogo da memória')`, não `t('play.memory.title')`.

O app tem **~1.800 a 2.200 strings de interface** medidas. Um catálogo de chaves simbólicas
exigiria batizar cada uma, manter o arquivo português em paralelo e revisar tudo antes de a
primeira tela funcionar — e uma chave errada não quebra teste nenhum, só aparece como buraco na
tela. Com o português como chave:

- **migrar é mecânico e reversível** — envolver a string em `t(...)`, sem inventar nome;
- **o fallback é o próprio português**, então tradução ausente nunca deixa a tela vazia;
- **a migração é incremental de verdade**: uma tela traduzida convive com dez não traduzidas.

O preço, cobrado à vista: mudar o texto português troca a chave, e aquela frase volta ao português
até alguém atualizar o catálogo. `node scripts/i18n/orfas.mjs` lista essas chaves; com
`--progresso`, mede quanto da interface já passa por `t()`.

**Sem biblioteca.** i18next resolveria o mesmo com ~40 kB gzip, detecção, plural CLDR e namespaces.
Nada disso é necessário: um idioma por vez, plural de duas formas, e o catálogo viaja pelo mesmo
caminho da trilha (`public/`, sob demanda, cacheado pelo CDN).

## O que "todos os idiomas" exige, e onde estamos

Traduzir palavras é a parte fácil. Estas quatro sustentam o resto — e três já estão feitas:

| | estado |
|---|---|
| **Plural pelo CLDR** | feito. `Intl.PluralRules`, nativo |
| **RTL** (árabe, hebraico) | feito. `dir`/`lang` no `<html>` acompanham o idioma |
| **Números e datas no locale** | os helpers existem (`numero`, `data`); faltam ~50 pontos migrados |
| **Tradução por falante nativo** | **não feito** — é o gargalo real, ver abaixo |

### Por que "n === 1" não serve

"Uma ou muitas" é a regra de português, inglês e espanhol — e de mais ninguém. Medido com
`Intl.PluralRules` nos dezesseis idiomas que já têm trilha:

| formas | idiomas |
|---:|---|
| 1 | japonês, chinês, coreano |
| 2 | português, inglês, espanhol, francês, alemão, italiano, holandês, sueco, turco, híndi |
| 3 | russo, polonês, hebraico |
| **6** | **árabe** (zero, um, dois, poucos, muitos, outro) |

**Seis dos dezesseis não cabem em duas formas.** Por isso `tp()` usa o CLDR do runtime, e o
catálogo guarda as categorias que cada idioma pede:

```json
"{n} palavras": { "one": "{n} слово", "few": "{n} слова", "many": "{n} слов" }
```

Categoria ausente cai em `other` — a única que todo idioma tem.

### O gargalo verdadeiro: quem traduz

A infraestrutura escala para N idiomas sem tocar em código. **O conteúdo não.** Hoje as traduções
são escritas aqui, sem falante nativo revisando, e isso tem limite claro: dá para escrever inglês e
espanhol defensáveis, não japonês ou árabe que alguém queira ler.

São ~2.000 strings por idioma. Antes de prometer dez idiomas, é preciso decidir **quem traduz** —
plataforma de tradução colaborativa (Weblate, Crowdin), tradutores contratados, ou comunidade. O
catálogo em JSON simples foi escolhido também por isso: é o formato que qualquer uma dessas
plataformas importa.

E há um custo que cresce com o número de idiomas: **mudar o texto português troca a chave**. Com
dois catálogos é gerenciável; com quinze, cada ajuste de redação exige revisar quinze arquivos.
`scripts/i18n/orfas.mjs` mostra o estrago, mas quem conserta é gente.

## Como usar

```ts
import { t, tp } from '../lib/i18n';

t('Jogo da memória')                                    // → "Memory game" em inglês
t('{n} palavras prontas', { n: 42 })                    // interpolação só de {chave}
tp(n, '{n} palavra pronta', '{n} palavras prontas')     // plural de duas formas
```

Fora de componente, `t()` basta. Em componente que precisa **reagir** à troca de idioma sem ser
filho do `App`, use `useI18n()`.

O idioma da interface **segue "meu idioma"** do perfil (`useIdiomaDaInterfaceSeguindoOPerfil`, na
raiz do `App`). Não há preferência separada: `mine` já é "o idioma que você já fala e o das
traduções que você lê", e perguntar de novo criaria o estado incoerente de quem diz falar alemão e
lê a tela em português.

## O que já está traduzido

| | strings | como |
|---|---:|---|
| Tabela `COPY` do perfil | 150 | `copyDoPerfil` traduz no ponto de saída |
| Títulos e descrições dos 9 jogos | 63 | `tituloDoJogo` / `descricaoDoJogo` |
| Menu de navegação | 36 | `navLabel` traduz no ponto de saída |
| Nome dos idiomas dentro de frases | todos | `langLabelNaUI` usa `Intl.DisplayNames` no idioma da UI |
| Títulos de tela e de painel (`panelMeta`) | 20 | `t()` no ponto de leitura |
| Motivos de descarte (`quality.ts`) | 27 | `t()` na UI — o núcleo devolve o português |
| Avisos de conta, guia, motores de IA, objetivos, filtros do mapa | ~47 | `t()` no ponto de leitura |

Catálogos: `public/i18n/en.json` (325 chaves), `public/i18n/es.json` (20).

A `COPY` do perfil é a maior fonte de texto do app — 54 chaves × 3 públicos, usadas em Estudo,
Vocabulário e Análise. Uma linha em `copyDoPerfil` cobriu as 150, porque ela já era o ponto único
de saída e já interpolava `{n}` com a mesma sintaxe do `t`.

O padrão vale para o resto: **traduzir no ponto de saída, não na tabela**. As tabelas de rótulo
seguem legíveis como a fonte da redação, e as variantes por perfil (kids/pro/senior) continuam
sendo escolhidas *antes* de traduzir — "Minhas Aulas" e "Sessão" são frases diferentes, cada uma
com a sua tradução.

## O que falta, em ordem de custo

1. **~400 strings ainda em tabelas de rótulo** (`LangAudit` ~30, `panelMeta` 20, `exigeConta` 20,
   `appearance` 20, `loja`, `marcosDeConta`, `galeria/textos`…). É o caminho mecânico: um helper
   por tabela, como os três que já existem. As tabelas de `src/core` são caso à parte — o núcleo
   não importa `lib/`, e não deve: elas devolvem o português e a UI traduz no ponto de exibição.
2. **~1.100 espalhadas em JSX** nas views e minigames. Concentradas: `Analysis.tsx` 129,
   `LiveCapture.tsx` 79, `Library.tsx` 51, `Reading.tsx` 49, `Settings.tsx` 38.
3. **688 casos de texto rico** — frases com `<b>`/`<span>` no meio. Cada uma precisa virar uma
   string com marcador ou ser quebrada; é o trabalho mais delicado.
4. **540 template literals** com `${}` — viram `t('...', { valor })`.
5. **~60 plurais**, alguns com concordância verbal (`já caiu` / `já caíram`) e alguns por sufixo
   (`erro${n > 1 ? 's' : ''}`), que não sobrevive à tradução.
6. **~50 pontos de locale** com `'pt-BR'` cravado (`toLocaleString`, `toLocaleDateString`). Precisam
   seguir o idioma da interface.
7. **O onboarding não pergunta o idioma da pessoa** — só o que ela estuda. Um estrangeiro fica em
   português por padrão até achar Ajustes.

## Armadilhas para quem for extrair strings

Parecem texto de tela e **não são**:

- **Chaves de união discriminada em português**: `'trilha-sem-frase'`, `'sem-pista'`,
  `'palavra-curta'`, `'segunda-sessao'`, `'kids'|'pro'|'senior'`. São identificadores.
- **~55 chaves de `localStorage`** `babel.*`. Traduzir = perder dados do usuário.
- **`LANGUAGES[].label`** são **endônimos de propósito** (`Español`, `日本語`): na lista de escolha
  a pessoa procura o próprio idioma escrito como ele é. Dentro de frase, use `langLabelNaUI`.
- **Corpus e regras linguísticas** (`quality.ts`, `expressoes.ts`, `fillers.ts`) e **prompts de
  LLM** (`ichatContext.ts`). São dados de processamento, não tela — embora os prompts *devessem*
  seguir o idioma da UI, decisão à parte.
- `t()` de `lib/profile.ts` foi renomeado para **`copyDoPerfil`**: ele lê a tabela por perfil, não
  traduz, e o nome `t` colidia com o de i18n dentro do mesmo arquivo.
